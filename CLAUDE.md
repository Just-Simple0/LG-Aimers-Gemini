# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Dacon competition entry for **"Aimers 9기: 투구 제구 성공 확률 예측 AI 온라인 해커톤"**
(LG AI Research / Dacon). Each row is one KBO pitch; the task is to predict
`control_success` — the probability (0–1) that the pitch was a "controlled" pitch —
using only information available **before** the pitch is thrown.

There is no application code yet, only baseline notebooks and the competition's
raw data/rules. Work here is almost entirely data science: feature engineering,
model training, and producing a submission zip that the grading server executes.

## Data

All data lives in `data/` and is described column-by-column in
[docs/data_description.md](docs/data_description.md) — read it before adding features.

- `train.csv` — 1,475,092 rows × 49 cols, seasons 2019–2024, includes the target `control_success`.
- `test.csv` — schema-only in this repo (5 sample rows, 48 cols). The real eval set
  (245,789 rows, season 2025) is injected by the grading server at the same path.
- `trackman_history.csv` — 1,793,078 rows × 30 cols of raw 2019–2024 Trackman logs
  (pitch velocity, spin, movement, etc.), **not** used by the baseline. Not joinable
  1:1 with train/test — it's a source for building your own historical features.
- `sample_submission.csv` — submission schema: `row_id, control_success`.

**Feature set is driven by `test.csv`'s columns, not `train.csv`'s.** The baseline
reads `test.csv` header first and trains only on columns present there
(`train.csv` has extra columns that don't exist at inference time and must not be used).

### Hard anti-leakage rules (from data_description.md)

These are competition rules, not suggestions — violating them invalidates a submission:

- Never use information that is only known after the current pitch resolves (actual
  location/course, actual result/call, actual pitch type, current-pitch Trackman
  measurements, 2025 Trackman data).
- Every row of `test.csv` must be predicted **independently**. Never compute
  aggregates, frequencies, target encodings, or rolling/expanding stats across rows
  of `test.csv` itself — only the provided `asof_*` columns (pre-computed,
  as-of-pitch-time stats) and `trackman_history.csv` (2019–2024 only) may be used
  for historical features.

## Evaluation metric

Brier Skill Score, scaled to 0–100000:

```
BrierScore     = mean((p_i - y_i) ** 2)
baseline_brier = r * (1 - r)          # r = mean control_success rate of the eval set
Score           = max(0, 100000 * (1 - BrierScore / baseline_brier))
```

Because scoring is on raw Brier Score, **probability calibration matters as much as
ranking/AUC** — a well-ranked but poorly-calibrated model scores worse than a
calibrated one. Validate with this exact formula (see the training notebook, section 5)
before trusting local improvements.

- Public score == Private score (same 100% of eval data, no train/test leaderboard split).
- Certification (수료) threshold: Public Score ≥ 549.51.
- Top ~100 teams undergo a second-stage code/PPT audit.

## Submission format (what the grading server runs)

Submissions are a **code** zip, not a predictions CSV. `submissions/baseline_submit.zip`
is a reference example (Dacon-provided, RandomForest) with this layout:

```
model/rf.pkl        # trained pipeline (pickled via joblib)
script.py           # inference entrypoint the server executes as-is
requirements.txt    # pip packages needed by script.py
```

`script.py` must, on a fresh offline machine: load `./model/*`, read
`./data/test.csv` + `./data/sample_submission.csv`, predict `control_success` for
every `row_id` in submission order, and write `./output/submission.csv`. Note that
`./` here means the extracted zip's own root — `src/script.py` in this repo always
uses `./data`, `./model`, `./output` (never `../`), since `model/` and `script.py`
sit side-by-side once unzipped.

Each versioned submission (`submissions/vN_<short-tag>.zip`) is built by copying
`model/<artifact>.pkl` (gitignored, regenerated by the train notebook), `src/script.py`,
and `src/requirements.txt` into a flat `model/`, `script.py`, `requirements.txt` layout
and zipping.

### Grading environment constraints

- **Submission filename ≤ 30 characters** (including `.zip`) — Dacon rejects longer
  names. Keep version tags short, e.g. `v2_lgb_cat_blend.zip`, not a full description.
- Full inference over 245,789 rows must finish in ≤ 10 minutes; package install ≤ 10 minutes.
- Zip ≤ 10GB (≤ 32GB unpacked). Runs fully offline except for the initial `pip install`.
- Runtime: 6 vCPU / 28GB RAM / L4 GPU (22.4GiB VRAM).
- Only models/weights under a license that is publicly available and at least
  non-commercial-use-permitting (MIT, Apache-2.0, etc.) may be used. No remote-API
  models (OpenAI, Gemini, etc.) — everything must run and be reproducible locally.
- Submission language is Python only; max 5 leaderboard submissions/day.

## Current pipeline (LightGBM + CatBoost ensemble)

The RandomForest baseline above has been replaced. `notebooks/train.ipynb` and
`notebooks/inference.ipynb` implement the full train → submit cycle; `src/script.py`
is the inference notebook's cells with paths adjusted for the zip's flat layout (see
each notebook's intro cell for the exact `../` vs `./` convention).

1. **`notebooks/train.ipynb`** — reads `test.csv` header to fix `FEATURES`, builds
   static count-state lookup tables by aggregating `trackman_history.csv` on
   `(balls_before, strikes_before, outs_before)` — the only keys shared with train/test
   that don't require player/team identity, since `trackman_history`'s
   `pitcher_trackman_id`/`batter_trackman_id` and `pitcher_team`/`batter_team` codes
   have zero reliable overlap with `train.csv`/`test.csv`'s `pitcher_id`/`batter_id`/
   `pitcher_team_id` (verified directly). **Two lookups are built, season-split**:
   `TK_LOOKUP_VAL` (seasons ≤ 2023, used only for the season-2024 holdout validation
   below) and `TK_LOOKUP_FULL` (seasons ≤ 2024, used only for the final full-data
   retrain/artifact). This split matters — an earlier version built one lookup from all
   of 2019–2024 and used it for both validation and the final model, which let 2024's
   own Trackman data leak into the "2024 holdout" validation score (caught via PR #3
   code review); the 2025 submission path itself was never affected, only the internal
   validation number was optimistic. Then builds 38 row-independent engineered features
   (`build_features()` — count-state/leverage interactions, cold-start-smoothed `asof_*`
   rates, matchup diffs, pitch-mix and cyclical encodings, plus 12 features merged from
   the passed-in `tk_lookup` and this pitcher's deviation from the league's count-state
   pitch mix; the merge uses `validate="many_to_one"` to guard against duplicate lookup
   keys — a `same_hand` hand-matchup dimension was tried as a fourth lookup key in v5
   but rejected after an ablation showed it made the holdout score worse, -1.41, once
   blend weight was held fixed; see the v5 experiment history in README.md; v8 added 3
   `li` (leverage index) derived features — `is_high_leverage` (`li >= 1.5`, threshold
   chosen by inspecting `train.csv`'s actual `li` distribution: mean 0.98, median 0.80,
   `li >= 1.5` covers the top ~19.7%), `li_count_diff` (`li * count_diff`), and
   `li_late_close` (`li * late_and_close`) — kept after an ablation showed +8.03 on the
   identical 2024 holdout; see the v8 experiment history in README.md), trains
   **LightGBM** and **CatBoost** separately (validated by holding out season 2024 with
   `TK_LOOKUP_VAL`, early-stopped), then runs a **KFold(shuffle=True, n_splits=5,
   random_state=42) out-of-fold** pass (`kfold_oof()` — splits the already-engineered
   training rows into 5 random folds and, for each fold, trains fresh LightGBM/CatBoost
   models on the other 4 folds and predicts the held-out fold, returning the two models'
   OOF predictions **separately**, unblended).

   **v10 replaced the W_GRID blend-weight/calibration-order grid search (v5–v9) with a
   logistic-regression meta-learner (stacking)**: a plain `sklearn.linear_model.
   LogisticRegression` is fit on `[lgb_oof, cb_oof] -> y_oof` (the same KFold OOF used
   for calibration in v5–v9 — judged low-risk to reuse for a 2-feature linear
   meta-learner, since it has essentially the capacity of a constrained weighted blend;
   see the v10 experiment history in README.md for the full reasoning and the
   scikit-learn `StackingClassifier` precedent this follows). Both the meta-learner's
   raw `predict_proba` output and a version with one more isotonic calibrator fit on top
   (mirroring v5–v9's blend-then-calibrate pattern) were tried against the 2024 holdout;
   **raw won** (782.47 vs 770.21 isotonic-on-top, both vs the v8-li baseline of 774.07) —
   the opposite of what was assumed going in, consistent with linear-stacking-sharpens-
   probabilities research (see README.md's "v10" section). The chosen (raw, no
   calibrator) design is refit on all seasons with `TK_LOOKUP_FULL` (fixed round counts
   from validation) using the same KFold-OOF-then-fit procedure, and everything is saved
   to `../model/ensemble.pkl` via `joblib.dump` — both base models, the fitted
   `stack_model` (`LogisticRegression`), feature list, `global_mean`, `tk_lookup`
   (= `TK_LOOKUP_FULL`). The old `blend_w_lgb`/`calibration_mode`/`calibrator`/
   `calibrator_lgb`/`calibrator_cb` artifact keys are gone — replaced entirely by
   `stack_model`. `trackman_history.csv` is only read at training time; `tk_lookup` is
   baked into the artifact so inference never needs the file.

   **History of the calibration-OOF mechanism (issue #4 / PR #5 / v7):** v1–v3 used
   `KFold(shuffle=True)` for this OOF. PR #5 (issue #4, GPT Pro 4th-round review) pointed
   out this wasn't strictly leakage-free — `asof_*` features are time-cumulative per
   pitcher/batter, so a random split can let a later pitch's training-row features leak
   an earlier pitch's own outcome into that earlier pitch's OOF prediction (not a
   competition anti-leakage violation, since it never touches `test.csv` — but not a
   strictly clean internal calibration OOF either). v4–v6 replaced it with a season-wise
   **expanding-window** OOF (`expanding_window_oof()` — for each held-out season `Y`,
   train fresh models on only `season < Y` data, with `global_mean`/`tk_lookup` also
   recomputed from that cutoff, so no fold ever sees information from its own or a later
   season). This was more rigorous in theory, but a dedicated investigation (local
   2024-holdout A/B/C experiment, see README.md's "v7" section) found it scored
   noticeably lower locally than the original KFold approach (~15pts lower) and
   coincided with three straight real Dacon leaderboard regressions (v3 KFold: 882.11 →
   v4/v5/v6 expanding-window: 871–877) despite each of v4/v5/v6 showing local
   *improvements* over its predecessor — the opposite of what local validation predicted.
   **v7 reverted the calibration-OOF mechanism back to `KFold(shuffle=True, n_splits=5,
   random_state=42)`** (`kfold_oof()`, described above) while keeping every other
   issue #4/PR #5 fix intact (the `TK_LOOKUP_VAL`/`TK_LOOKUP_FULL` season split above is
   a *different* leak-prevention fix and was never reverted). This re-accepts the same
   minor OOF circularity v1–v3 always had, on the strength of v3's real-world track
   record — see README.md's "v7" section for the full experiment table and caveats
   (local score is not this change's real acceptance bar; a fresh Dacon resubmission is).
2. **`notebooks/inference.ipynb`** — loads `../model/ensemble.pkl`, reads
   `../data/test.csv` + `../data/sample_submission.csv`, rebuilds the same engineered
   features via `build_features()` (using the artifact's `tk_lookup`), gets both models'
   `predict_proba` output, stacks them into a 2-column array `[p_lgb, p_cb]`, and calls
   `stack_model.predict_proba(...)` (v10 — replaces the old blend-weight/calibration-mode
   branch) to get the final probability directly, with no additional calibration step.
   Merges predictions back onto `sample_submission`'s `row_id` order (unmatched rows keep
   the placeholder value), and writes `../output/submission.csv`.

Because feature engineering is plain Python (`build_features()`), not bundled inside a
sklearn `Pipeline`, any change to it in the training notebook must be mirrored
character-for-character in `src/script.py`'s `build_features()` (and in
`notebooks/inference.ipynb`, adjusting the `../` vs `./` path prefix as needed), or
inference will silently diverge from training.

To produce a submission: run `notebooks/train.ipynb` to (re)generate
`model/ensemble.pkl`, then copy `model/<artifact>.pkl` (as `model/ensemble.pkl`),
`src/script.py`, and `src/requirements.txt` into a flat zip (see
[README.md](README.md) for the exact commands) and name it
`submissions/vN_<short-tag>.zip` — short enough to stay under Dacon's 30-character
filename limit, but still descriptive enough (not just `submit.zip`) that the
experiment history stays legible.

Every new experiment stage gets its own `experiment/vN-<description>` branch,
PR'd and merged into `main` (see README.md's "실험 워크플로" section) — this is how
prior submissions (e.g. the 848.64484-scoring v1) stay recoverable instead of being
silently overwritten by the next round's retrain.
